# Database Schema Documentation

**Project:** Hardware Service & Repair Booking Platform  
**Database:** PostgreSQL  
**ORM:** Spring Data JPA / Hibernate  
**Source of truth for this document:** The ten Java JPA entity classes and five enum classes in `serviceplatform/src/main/java/com/hardware/serviceplatform/`.

> **Schema accuracy note:** This document describes the schema implied by the current JPA entity mappings. It is not a database dump from the deployed PostgreSQL instance. Hibernate's physical naming strategy, PostgreSQL version, and any existing database-side changes can affect the final deployed schema. Confirm the live schema against PostgreSQL before treating this as a production migration script.

## 1. Overview

The application models users, engineer profiles and skills, service categories, bookings, booking status history, assignment history, quotations, payments and customer feedback.

| Table | Purpose |
|---|---|
| `users` | Customer, engineer and administrator accounts |
| `engineer_profiles` | Engineer service area, coordinates, availability and working hours |
| `service_categories` | Hardware/device service categories |
| `engineer_skills` | Service categories and service types supported by each engineer |
| `bookings` | Customer repair/maintenance/installation/diagnosis requests |
| `booking_status_history` | Audit trail of booking status changes |
| `assignment_history` | Audit trail of engineer assignment and reassignment |
| `quotations` | Labour, parts and additional charge estimates for a booking |
| `payments` | Simulated payment records for quotations |
| `feedback` | Customer rating and comment for a booking |

## 2. Data type conventions

The SQL types below are the expected PostgreSQL equivalents of the Java/JPA types used in the project:

| Java/JPA type | PostgreSQL type |
|---|---|
| `Long` with `GenerationType.IDENTITY` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| `String` | `VARCHAR(255)` unless a different length is specified |
| `String` with `@Column(length = n)` | `VARCHAR(n)` |
| `Integer` | `INTEGER` |
| `Double` | `DOUBLE PRECISION` |
| `Boolean` | `BOOLEAN` |
| `BigDecimal(precision=10, scale=2)` | `NUMERIC(10,2)` |
| `LocalDateTime` | `TIMESTAMP WITHOUT TIME ZONE` |
| `LocalTime` | `TIME WITHOUT TIME ZONE` |
| `EnumType.STRING` | `VARCHAR` storing the enum constant name |

All primary keys are generated using identity generation. Unless a different length is stated, strings use the JPA default length of 255.

## 3. Table definitions

|---|---|---|

**Role values:** `CUSTOMER`, `ENGINEER`, `ADMIN`.

### 3.2 `engineer_profiles`

## 6. Important implementation notes

1. **Nullable timestamps:** Several timestamp fields are populated by `@PrePersist` but are not marked `nullable = false`. Their JPA mapping therefore does not explicitly declare a NOT NULL constraint.
2. **Java defaults versus database defaults:** Initial values such as `available = true`, `active = true`, `serviceRadiusKm = 15.0`, and enum defaults are Java field initializers. They should not be described as PostgreSQL `DEFAULT` constraints unless the deployed database confirms those defaults.
3. **Feedback rating:** The 1–5 range is expressed using Jakarta Bean Validation annotations. Confirm whether database CHECK constraints also exist before describing them as database-enforced.
4. **One-to-one relationships:** `unique = true` on the relevant join columns enforces at most one profile per user, quotation per booking, payment per quotation and feedback record per booking.
5. **Engineer skill uniqueness:** The composite unique constraint prevents duplicate combinations of engineer profile, service category and service type.
6. **Booking assignment:** `engineer_profile_id` is nullable so a booking can exist before an eligible engineer is assigned.
7. **History actor fields:** `changed_by_user_id` and `assigned_by_user_id` are nullable to allow system-generated events or events without a recorded user actor.
8. **No separate device table:** The device category is represented by `service_categories`; device details are not stored in a dedicated device entity in the current entity model.

## 7. Schema management

The backend configuration currently uses Hibernate schema auto-update (`spring.jpa.hibernate.ddl-auto=update`). This allows Hibernate to update the database schema based on entity mappings during application startup.

For a production system, use version-controlled database migrations (for example, Flyway or Liquibase), review generated DDL and apply schema changes through controlled deployment steps.
